# 数字人口语陪练 — 产品设计逻辑

> 2026-10-14 最新体验：数字人是主界面，默认自由对话；主动开始后可从顶部练习面板选本地文本课程。有真实最近课时开场询问继续，按钮与语音共用业务能力。“好”仅消费已经实际播完的询问。Agent 主动理解并调用工具，规则承担校验与有限短指令兜底；失败不能口头声称完成。明确长期偏好才保存，临时练习需求不保存；英语水平仍由证据更新。第 0–5 步实现与体验边界见 [整体交付](avatar-practice-delivery-2026-10-14.md)，以下旧阶段范围为历史。

> 2026-10-14 入口调整：已确认伙伴后，数字人对话页成为主界面。进入先静默准备画面，点击开始才播放开场，主动语音才申请权限并采集。60 秒未开始释放连接，保留主界面；伙伴与设置从左上角进入，浏览设置保持媒体连接，应用新伙伴才重建。候选选择与已确认选择分开。第 1 步实现与真机验收边界见 [交付记录](avatar-practice-stage-one-2026-10-14.md)；课程和 Agent 管理工具仍按后续步骤实施。

> 2026-10-13 第一阶段范围：账户、数字人首页、统一对话和“我的”。注册只问账号密码；练习目标和兴趣从真实对话逐步获取，用户可在“我的”修改或删除，不连续盘问。英语水平数据不足显示“正在了解”，充足近期独立回答后显示能力描述，不显示内部等级和分数。教材添加/训练、练习回顾与记录暂不做；提醒、登录设备和账号数据管理后续补齐。后端接入契约见[`phase-one-api.md`](./phase-one-api.md)。

## 0. 一图看懂

```
                    产品目标：让不敢开口的人，愿意继续说
                                │
        ┌───────────────────────┴───────────────────────┐
        │            两条准入要求（可执行契约）            │
        │   ① 零评判（不说错、不报分、一轮最多一条升级）    │
        │   ② 会追问（每轮一个基于具体细节的问句）          │
        └───────────────────────┬───────────────────────┘
                                │
   ┌────────────────────────────┼────────────────────────────┐
   │                            │                            │
场景人设                    分级语言策略                  数字人介质
「我是谁」                 LOW / MID / HIGH             画面 + 语音 + 字幕
Amy / Alex                比场景设定更重要              脚本轨管「已定的话」
   │                            │                            │
   └────────────────────────────┼────────────────────────────┘
                                │
                     一轮对话（说的顺序与节奏）
   App 录音 ─ STT ─ 发音评测 ─ 归档 ─ 定档 ─ Agent 生成 ─ 整段 /say ─ 字幕
                                │
                        评测数据的可见性边界
                  给模型看（内部数据） ≠ 给用户看（不报分）
```

**三条设计公理**（本页其余内容都可以从这三条推导出来）：

1. **学员最大的障碍不是「不会」，是「怕被评判」。** 所以这个产品不是纠错工具，是「让他愿意继续说」的工具。
2. **质量指标是追问率，不是答对率。** 数字人能不能就着学员刚说的具体细节再挖一层，才是这个产品有没有做出差异。
3. **难度跟着学员走，不跟着场景走。** 场景只决定「我们聊什么」，学员这一轮说得怎么样才决定「我用什么语言陪」。

## 1. 产品定义与反定义

### 1.1 是什么

- **一句话**：用户对着手机说英语，屏幕上有一个数字人形象用英语陪他聊，语音进出、字幕可见。
- **目标用户**：想开口说英语、但缺乏真实对话机会或心理压力的中文母语者（学生 / 求职者 / 职场人）。
- **核心场景**：`free`（自由对话，练开口的胆量）、`interview`（英文面试，练自我介绍与常见问题）。
- **介质**：数字人（画面 + 语音）+ 字幕 + 跟读发音卡片。

### 1.2 反定义（明确不做的事）

| 不做 | 为什么 |
|---|---|
| 不做「错题本 / 纠错报告」 | 报告=评判，评判=压力，压力=不再开口。这是产品取向的第一道红线。 |
| 不在对话里报分数、报等级 | 一旦用户感觉到「系统在给我打分」，一切都回到考试语境。 |
| 不做「万能追问」（And you? / Tell me more） | 这类追问等于没听，学员三轮内就识破，产品差异化归零。 |
| 不把用户档位显示在界面上 | 显示=打标签，与零评判冲突。 |
| 不在数字人的话里出现音标符号 / markdown | 这些话要被 TTS 念出来，符号读不出来，也听不懂。 |

## 2. 两条准入要求（人格契约）

这两条是「能不能上线」的准入条件，不是「尽量做到」的体验优化。它们被写成了**可执行的契约**，落在两个地方：

| 契约 | 落点 | 性质 |
|---|---|---|
| 零评判 / 单任务 / TTS 格式 | `spoken-server-app/src/main/resources/agent/spoken-server.yml` 的 `instruction` | **不变量**：每个短会话的 SYSTEM 基础指令 |
| 六级档位、语言策略、唯一任务与本轮结果；用户原话与历史分开传入 | `spoken-server-domain/src/main/java/cn/adinall/ai/domain/conversation/service/reply/ReplyPromptBuilder.java` | `buildSystemPolicy` → SYSTEM；`buildManaged` → USER |

> **当前实现（2026-10-13）：** 等级语言规则通过短会话 state 的 `turn_policy` 注入 SYSTEM，优先于历史。用户原话、场景和记忆留在 USER；历史裁剪会预留动态系统规则的容量。理解求助（例如“你说的是什么？”）优先于纯中文跟读，不改冻结等级。

### 2.1 第 ① 层：零评判

| 要求 | 具体做法 |
|---|---|
| 不许说错 | 禁用措辞：`wrong` / `incorrect` / `mistake` / `error` / `mispronounced` / `you should have` / `try harder` / `again` |
| 要改就「提供升级」而不是「报告错误」 | 话术固定为 `A more natural way to say that is ...` / `Native speakers usually say ...` / `Try it this way: ...` |
| **一轮最多提一条** | 提多了就是罚单。宁可不提，也不挑刺。 |
| 不许报分数、不许提「评测」 | 模型很爱在回复里报数（"your score is 86"），提示词里必须反复钉住「学员看不到这些数据」 |
| 学员卡住时降标准、给安抚 | "No rush, we're just chatting." 让学员永远不觉得「我失败了」 |

### 2.2 第 ② 层：会追问

- **每一轮回复必须以恰好一个问句收尾。**
- 问句必须**建立在学员刚说的具体细节上**（他提到飞盘 → 问在哪玩、和谁去、怎么开始的），而不是「你喜欢吗」。
- **禁止复述 / 转述学员原句** —— 只会鹦鹉学舌的回复，学员三轮内就识破。
- **同一话题要连续挖几轮**，把线索用尽再换，换的时候要带走一个衔接点。
- 数字人要有**自己的小观点和小反应**，让对话是双向聊天，不是面试。

### 2.3 怎么验证契约被遵守（重要）

- 人格契约是自然语言约束，**唯一可观测手段是回复原文**。因此 `ConversationServiceImpl` 把每条回复原文打进日志：`回复已下发 ... text=...`。
- 提示词尾部再钉一次「用一个具体问题收尾」：系统指令里虽有约定，但**每轮消息尾部重复一次，实测遵守率明显更高**。
- 排查人格问题只看两处：`agent/spoken-server.yml` 的 `instruction`（不变量）与 `ReplyPromptBuilder`（每轮变量）。

## 3. 分级语言策略（本产品最核心的个性化机制）

产品判断：**「用英语陪练」不等于「全程说英语」。** 对撑不住的学员，全程英语的结果是他沉默或者逃回中文 —— 那这个产品就白做了。所以语言比例必须跟着学员的**实际表现**动态调整。

### 3.1 三档策略

| 档位 | 语言策略 | 产品意图 |
|---|---|---|
| `LOW` | **主要用中文陪**，给一句 3~6 词的英文示范让他借用，并用中文邀请他跟读 | 绝不能让他卡住；先恢复「说话」这个行为本身 |
| `MID` | 简单英文短句；只有某个词可能生僻时，后面括注 2~4 字中文 | 用可理解的英文输入慢慢加量 |
| `HIGH` | 全英文，不允许出现任何中文字符 | 自然、地道的英语输入 |

三档的**行为细节**写在 `instruction` 里，每轮只下发「这轮用哪种语言」——职责单一，行为才可控。

### 3.2 档位怎么判（`LearnerLevelTracker.judge`）

| 信号 | 分值 | 设计理由 |
|---|---|---|
| 完全没识别出内容 | −2 | 说不出来，是最强证据 |
| 文本含中文 | −2 | **学员逃回母语了**，最直接的「撑不住」信号 |
| 英文词数 1~2 | −1 | 只答一个 Yes/No，内容量不足 |
| 英文词数 ≥ 8 | +1 | 能组出完整长句 |
| 评测分 < 60 | −1 | 发不准 |
| 评测分 ≥ 85 | +1 | 又准又长 |

- 合计 **≥ 1 → HIGH**；**≤ −2 → LOW**；否则 **MID**。
- **LOW 的门槛刻意设成 −2 而不是 −1**：单个弱信号证据不足。否则学员答一句 "Yes" 就被切到中文档，体验很突兀。**要「说不出内容」和「发不准」同时出现（`Yes` + 52 分），才判定他真的撑不住。**
- 词数只数「含拉丁字母」的片段：识别结果里混着标点和中文，按空格数会把 `我不知道` 也算成一个词，反而漏掉证据。

### 3.3 滞后控制（`accept`）——两条方向性决策

| 规则 | 取值 | 产品理由 |
|---|---|---|
| **下调立刻生效** | 1 轮 | 学员一旦露怯要立刻接住，不能等 |
| **上调必须攒** | 连续 **2** 轮同向信号 | 提高难度得确认他不是碰巧说顺了一句 |
| **一次只挪一档** | LOW→MID→HIGH | 「慢慢引入到英文」；不会因为说顺两句就被丢进全英环境 |
| 无证据（既无文本也无评测） | 不动档位 | 没有证据就别动扶手高度 |

> 实测演进：中文 → LOW；英语 ×2 → MID；英语 ×2 → HIGH。

### 3.4 初始档位：自评优先，其次近期历史，最后场景默认

| 情况 | 会话初始档位 | 开场白 |
|---|---|---|
| **用户明确选择自评水平** | beginner → LOW / intermediate → MID / advanced → HIGH | 按用户选择的档位选，仅决定起点 |
| **无自评，有有效近期历史** | 用近期长期水平 | 按该档位选 —— **长期 LOW 的学员，开场就听中文** |
| **无自评、无有效历史** | 从场景难度起步（`advanced` → HIGH，其余 MID） | 按该档位选 |

- 会话内仍由 `LearnerLevelTracker` 演进（下调立刻、上调攒 2 轮、一次只挪一档）——
  **长期水平只决定起点，不封顶学员在会话里的爬升。**
- **为什么这不算评判**：原红线反对的是「**没有证据就假定**学员不行」—— 人还没开口、
  只因为场景写着 beginner 就按 LOW 招呼。长期水平是**学员自己的历史表现**攒出来的，
  拿它当起点是**连续性**。让一个长期撑不住的学员一上来就听全英文，才是真正的不友好
  —— 他会沉默，或者逃回中文。
- **两条护栏，少一条就会滑回评判**：
  1. 长期水平必须按**近期**表现算（滚动窗口 / 最近 N 场），不背历史总账 ——
     否则一次糟糕经历会把人永久钉在 LOW，那才是真的判了刑。
  2. 档位仍然**不出现在界面上**（见 §3.5）。开场说中文是「接住他」，不是「告诉他你很差」。

> ⚠️ **开场白没法自己适配档位**：它走脚本轨（`/say`，不经 LLM），没有模型替它改语言。
> 所以一个场景必须按档位存多份开场白（`opening_line_low/mid/high`），
> 优先级 `档位专属 → opening_line（默认）→ 不自动开场`。
> DDL 见 [`V8__scenario_opening_by_level.sql`](../../spoken-server-app/src/main/resources/db/migration/V8__scenario_opening_by_level.sql)，
> 验收说明见 [`user-data-model.md`](./user-data-model.md) §4.2.1。

### 3.5 档位是内部状态

- **绝不下发给 App 展示。** 一旦显示就变成「系统在给我打等级」，与零评判冲突。
- **会话内的运行档位不持久化**：仍是内存状态，随会话生灭（进程重启时上游会话也已失效）。
  会话结束时持久化有效信号的聚合证据，用于重新计算近期长期水平，不用于恢复运行态。
  但**起点**来自持久化的**长期水平**（见 §3.4）；长期水平按近期表现滚动计算，存在画像里。

## 4. 场景与人设

**场景是「内容」，不是「逻辑」。** 它只提供四件东西：

| 字段 | 用途 |
|---|---|
| `systemPromptHint` | `free` / `interview` 的专属提示已移除，两者统一用口语教练；其他场景字段保留为兼容扩展 |
| `openingLine`（+ `openingLineLow/Mid/High`） | 开场白，走**脚本轨**（不经 LLM）。**必须按档位存多份** —— 否则低档学员也只能听英文开场（见 §3.4）；优先级 `档位专属 → openingLine → 不自动开场` |
| `voice` | TTS 音色（脚本轨与生成轨共用） |
| `level` | **只在用户没有历史时**用于推初始档位；有历史则以长期水平为准（见 §3.4） |

当前两个场景（`spoken-server-infrastructure/src/main/java/cn/adinall/ai/infrastructure/adapter/repository/InMemoryScenarioRepository.java`）：

| id | 标题 | 人设 | 音色 |
|---|---|---|---|
| `free` | 自由对话 | 统一 SpokenCoach，无专属人设 | `Cherry` |
| `interview` | 英文面试 | 统一 SpokenCoach，无专属人设 | `Ethan` |

### 4.1 当前提示词入口

- `free` / `interview` 不再区分生成规则，不再传 Amy / Alex 或英语优先人设。
- `ScenarioVO` 屏蔽这两个旧入口的专属提示；V14 清理数据库官方场景的人设和阶段指令，旧迁移保持不变。
- 语言与任务规则只有一个本轮入口：`ReplyPromptBuilder.buildSystemPolicy` → case → `IChatService` → ADK state → SYSTEM。
- 当前输入独立标识为 `CURRENT USER UTTERANCE`；历史、上一轮练习目标不是用户本轮实际说出的内容。
- 请求“你说的是什么？”时先解释实际上一轮内容，再给一个简单问题；普通中文陈述仍遵循已有跟读策略。
- 场景编码和目录暂保留，以兼容现有客户端；数字人名称以当前形象配置为准。
- 教学模型温度设为 `0.1`，减少采样造成的语言与任务波动；同一输入、同一历史重试相同回复是允许的。
- 流式修复：HTTP 非空正文块都是真实增量，不能按 `.!?` 判断为汇总；正常结束后只给 ADK 一份完整汇总，播放端去重。引用中的问号不算另一个待回答任务，避免中文解释吞掉后续英文问题。

## 5. 一轮对话的产品逻辑（时序即体验）

### 5.1 用户视角

1. 选场景 → 数字人开口说开场白（**1 秒级**，因为走脚本轨）。
2. 按住说话 / 实时对话说一句英语。
3. 屏幕先出现「我」这侧的气泡（识别中 → 识别文本）；跟读开着时，这条气泡会挂上发音卡片。
4. 数字人开始回答：字幕随上游 TTS 分句出现，语音同步念出。
5. 需要时点「打断」；听不懂时点气泡上的「译」。

### 5.2 系统时序（`POST /api/v1/sessions/{id}/voice`，`llm-owner=agent`）

```
App 上传「已过 AEC3」的裸 PCM（octet-stream）
  → WavEncoder 封 WAV
  → OpenTalking /transcribe          只识别，不说话（老链路会让上游接着 LLM+TTS，已弃用）
  → 落一条只有 userText 的回合 + 推 stt.final（带 turnId）
  → OpenPronounce 评测（参照文本 = expectedText 或识别文本）
      → 落 pronunciation_assessment + 推 assessment.done
  → 判定本轮档位（识别文本 + 评测分 → 信号 → 滞后方档）
  → 拼提示词（人设 + 档位 + 语言策略 + 本轮文本 + 评测结论 → Google ADK agent 生成回复）
  → 模型写完整段后，一次性 /say 下发（数字人随后开口）
  → 上游 speech.ended → assistant.done：定稿字幕、复位播放状态、回填回合的 assistantText
HTTP 同步响应：{"text","turnId","assessment"}   ← App 靠它立刻收掉「正在识别」的转圈
```

### 5.3 这一段里的产品决策

| 决策 | 理由 |
|---|---|
| 评测插在 **STT 与 LLM 之间** | 迁移前上游是 STT+LLM+TTS 一条龙，评测根本插不进去。Java 接管 LLM 的全部意义就在这个插入点。 |
| **评测失败不阻断对话** | 上游抖动、音频太短都会让评测失败。它失败只降级成「这轮没有评测卡」，对话必须继续。 |
| 同步响应只做「识别 + 落库 + 评测」 | 这三件确定且快；回复生成放后台订阅，不让 HTTP 请求挂着等模型。 |
| 字幕 / 播放状态 / 回合落库都由**上游**驱动 | 迁移前的既有行为。上游每次 `/say` 发一轮 `speech.started` / `subtitle.chunk` / `speech.ended`，App 的字幕与「正在播放」状态都挂在这套事件上，落库也搭 `speech.ended` 的车。 |
| 回复**整段一次** `/say` | 逐句下发会产生 N 轮上游事件：字幕被定稿 N 次（`appendAssistantLine(final=true)` 在末行已 final 时会**新建气泡**）、播放状态每句闪一次、回合 `assistantText` 只留最后一句。要做流式必须先切开这三件事的归属。 |
| 首字延迟要盯 | 用户说完到模型吐第一个字，是「听得快不快」的真实体感，已打进日志（`firstDeltaMs`）。 |
| （已试过并**回退**）按句流式下发 | 2026-10-12 实现过一版：ADK 开 SSE（token 级增量，需显式传 `RunConfig(StreamingMode.SSE)`）+ 切句器 + 逐句 `/say` + 新增 `tts.end` 事件把播放状态从字幕定稿里切开。效果：交出文本后 **13ms** 就出音、句间 **1ms** 无缝隙，架构上也确实更干净。<br>但**端到端没有可测收益**：延迟大头是模型 TTFT（直连实测 2~15s，波动极大），流式省不掉它；同时多出一套事件协议与状态机（期间还踩了 `command_id` 撞 id 导致第二轮 409 的坑）。故回退到整段一次。**要再快只能换更快的模型/服务商。** |

## 6. 发音评测的产品定位

**这是最容易做错的一块。** 评测引擎能给出的东西（分数、错词、音素、韵律、错误率）里，**大部分不该进产品**。

### 6.1 可见性边界：给模型看的 ≠ 给用户看的

| 数据 | 给谁 | 怎么用 |
|---|---|---|
| 总分 + 错词候选（最多 3 条） | **只给模型**（内部数据） | 让模型判断「这轮值不值得提供一条温柔升级」 |
| 同上的结果 | App 气泡上的发音卡片 | 用户主动练习时的反馈载体 |
| 韵律曲线、音素向量、错误率 | 只进 HTTP 全量响应 | 供 App 画图 / 排查，**不进提示词** |

### 6.2 为什么提示词里只给「分数 + 错词候选」

- **不给韵律曲线、音素向量、错误率**：前两者是给 App 画图的；错误率对「这轮该说什么」没有增量信息，只会稀释模型注意力。
- **分数与错词必须同时给**：只给分数指不出具体哪个音；只给错词会让 90 分的小瑕疵被说成不及格。
- **错词上限压到 3**：长句可能报十几处错，全塞进提示词就成了一张罚单，模型反而抓不住重点。这 3 条是**候选池**，系统指令要求它最多只用其中一条。
- **明确写「学员永远看不到这些数据」**：模型很爱报数，一旦说出口就变成「系统在给我打分」，与零评判冲突。
- **提示词用英文写**：模型行为很容易被指令语言带偏 —— 用中文写指令，它更可能用中文回答。只有 LOW 档明确要求「用中文说」，那是**策略**，不是指令语言。

### 6.3 跟读模式：降低「开口」门槛的设计

- App 上有「跟读」开关：数字人说完一句后，把**那句话**钉为照读目标，显示在输入条正上方（不摆出来的话，用户得自己记住上一句，练习就变成回忆测试了），用户按住麦克风照读一遍。
- 后端 `POST /voice` 支持 `expectedText` 查询参数作为**参照题面**；不传则回退为识别文本。
- ⚠️ **已知偏差（待 App 接）**：Android 侧 `SpokenAiApi.voice` 目前没有 `expectedText` 参数，`followTarget` 只用于界面显示。因此实际评测参照 = 识别文本，**跟读分衡量的是「发音清晰度」而不是「照读准确度」**。要拿到真正的跟读准确度，需要 App 把题面随上传一起下发。
  - 对照：llm-wiki 待办里 App 侧接入尚未完成（[`llm-wiki.md`](./llm-wiki.md) §8）。
- 上游支持 7 种语言，但**只有英语对着人工评分校准过**（其余复用英语阈值）。产品上若要只放英语，把 `spoken-ai.provider.openpronounce.expose-languages` 配成 `[en]`。

### 6.4 评测数据的落库定位

- `pronunciation_assessment` 表：完整结果存 `result_json`，另存 score / 错误率等标量列供查询。
- 定位是「口语训练的数据来源」与将来做趋势 / 纠音产品化的地基，**当前不面向用户做报表**（与「不做错题本」一致）。

## 7. 数字人作为产品介质

### 7.1 双轨制：内容已定的话必须走脚本轨

| 轨道 | 端点 | 语义 | 首块音频（实测） |
|---|---|---|---|
| **生成轨** | `POST /sessions/{id}/speak` | `text` = **用户说的话** → 上游 LLM 生成回复再念 | ~6.9s |
| **脚本轨** | `POST /sessions/{id}/say` | `text` = **数字人要说的话** → 直通 TTS，不经 LLM | ~1.0s |

- **开场白、题目、讲解、判分反馈这类「内容已定」的话，必须走脚本轨。** 快 7 倍，且措辞完全可控。
- `/say` 也是为「外部（agent）驱动数字人念文本」预留的位子 —— 现在 Java 接管 LLM 后，正是 agent 出文本 → `/say` 念。
- **TTS 音色是唯一能同时管住两条轨的旋钮**（系统提示词只能管生成轨）。所以「强制英语」除了提示词，还要靠 `voice` 用英文音色 + 上游默认 TTS 引擎配套。

### 7.2 输出形态的产品约束（因为它要被念出来）

- **一到三句短句**，长了听着难受。
- **纯文本**：无 markdown、无列表、无 emoji、无舞台指示、不要整句加引号。
- 用**口语缩写**（`I'd love to` 而不是 `I would love to`）。
- **不许出现 IPA 或音标**；要示范读音就用中文字母重拼，例如 `weather: WEH-ther`。

### 7.3 打断

- 打断是**交互必需品**：用户听不懂或想插话时必须能立刻让数字人闭嘴，否则等待会变成压力。
- 打断后由我方**统一下发一条 `interrupted` 事件**收口字幕（界面上的「已打断」标记也靠它），不依赖上游是否回执。
- 「正在说话」按**上游真正出声的窗口**（`tts.start` ~ 会话结束）判，不按字幕定没定稿 —— 文本流比语音快得多，用字幕判会让打断键提前消失。

## 9. 异常与降级的产品语义

**核心原则：把「正常情况」和「故障」分清。** 把「用户没说话」判成 502，会让客户端把正常情况显示成故障，白白消耗用户耐心和排查时间。

| 情况 | HTTP / 语义 | 产品表述 |
|---|---|---|
| GPU 槽位被占，会话排队 | **409 session_queued** | 「数字人后端还在排队，请稍后重试」→ App 该等，不是错误 |
| 会话已结束（上游断开后释放了槽位） | **404 session_not_found** | 让 App **重新开始一次对话**（404 是 App 唯一不会重试的信号，不能落到 502 被当成语音问题） |
| 没听清 / 没有有效语音 | **400 no_speech** | 「没听清」，不是故障 |
| 音频超限 | **413 audio_too_large** | 录音太长 |
| 缺参数 / 空音频 | **400 invalid_request** | 请求问题 |
| 发音评测失败 | 不影响本轮 | 只是没有评测卡，对话继续 |
| Agent 生成失败 | 只推一条 `error` 事件 | **不把会话打成 ERROR**：一次回复失败不等于会话不可用 |
| 模型一个字都没回 | 不下发 | 别让数字人念空气 |
| 会话不存在（查询） | **404 session_not_found** | 「会话不存在或已结束」 |

**回退开关**：`spoken-ai.llm-owner: agent | opentalking`（默认 `agent`）。一条配置即可切回迁移前的老链路，用于对比与兜底。

## 10. 技术给的产品约束（必须当作产品事实）

| 约束 | 产品后果 |
|---|---|
| **数字人后端是单 GPU 槽**（整个会话生命周期只允许一个会话） | 同一时间只有一个用户能真的在对话，其他人排队（`session_queued`）。想多用户并发需要扩展方案。 |
| 排队中被 DELETE 的会话会变僵尸 | 既不取消也不释放队列计数，只能重启数字人引擎清理。联调期需频繁清理。 |
| **会话是进程内的** | 后端重启即丢，客户端重建会话。会话是短生命周期的。 |
| 首字延迟 | 用户说完到听见第一声 ≈ 识别 + 评测 + 模型首字 + TTS 首块。**延迟大头是模型 TTFT（直连实测 2~15s，波动极大）**，靠改下发方式省不掉 —— 逐句流式试过并回退，见 §5.3。 |
| 上游 `/say` 立即返回、不等播放完 | 下发只表示「受理」，真正的播放进度从上游的 `tts.start` 与 speech 事件读。这也是当初想逐句连发的依据（已回退）。 |
| 音色按引擎命名空间命名 | **换音色必须同时换 TTS 引擎**（`dashscope/Cherry`、`edge/en-US-AriaNeural`）。只换名字解不出来。 |

1. **App 侧接入收尾**（在 `jugao/android` 仓库）：
   - 截 AEC3 后 PCM 上传；**真机验证换自定义音频处理 factory 后 AEC3 仍开启**（唯一未验证的不确定项）。

   - 清理调不通的调试端点与调试落盘（`dbg-*.pcm`）。

5. **首字延迟**：已试过逐句流式并**回退**（§5.3）—— 结论是延迟大头在模型 TTFT，

6. **评测结果的产品化**：错词高亮、音素级纠音、分数趋势 —— 注意与「不做错题本」的红线取舍。
7. **多用户并发**：单 GPU 槽是硬约束，需要专用调研方案。
